# **Statement of Work for YanaTaskTracker. Техническое задание проекта**

> сгенерированно ИИ

## Контекст и принятые решения

YanaTaskTracker --- личное приложение для управления задачами. Первая версия
рассчитана на одного пользователя (владельца), но архитектура должна
допускать последующее добавление нескольких пользователей. SQLite
используется намеренно как временная учебная БД с последующей миграцией
на PostgreSQL. Использовать только SQLAlchemy 2.0, не SQLModel. Telegram
и напоминания не входят в MVP. Будущая привязка Telegram должна
подтверждать владение аккаунтом через одноразовый токен; нельзя
принимать произвольный `telegram_id` от клиента.

## Цели MVP

-   CRUD задач.
-   Статусы, приоритеты и сроки.
-   Поиск, фильтры и сортировка.
-   Простой веб-интерфейс.
-   Разделение HTTP-слоя, схем, сервисов и доступа к данным.
-   Автоматизированные тесты.

## Функциональные требования

Сущность `Task`: `id`, `title`, `description`, `status`, `priority`,
`due_at`, `completed_at`, `created_at`, `updated_at`. Название
обязательно и не может быть пустым после удаления пробелов. Статусы:
`todo`, `in_progress`, `done` (для упрощённого старта допустимы `todo` и
`done`). Приоритеты: `low`, `medium`, `high`. При переводе в `done`
фиксировать `completed_at`, при возврате в активный статус очищать.
Любое изменение обновляет `updated_at`. Время хранить в UTC.

Поддержать фильтрацию по статусу, приоритету и просрочке, поиск по
названию и сортировку по сроку, приоритету и дате создания. Просроченная
задача --- незавершённая задача с прошедшим сроком.

Интерфейс MVP: главная страница, форма создания/редактирования, фильтры,
отображение статуса/приоритета/срока, подтверждение удаления и ошибки
валидации. Рекомендуется Jinja2, HTMX опционально.

## Технологии

-   Python 3.12+
-   FastAPI
-   Pydantic v2
-   SQLAlchemy 2.0 (`DeclarativeBase`, `Mapped`, `mapped_column`)
-   SQLite на учебном этапе, PostgreSQL после миграции
-   Alembic, Pytest, Ruff
-   Docker и Docker Compose
-   Jinja2, опционально HTMX

SQLModel не использовать. Конфигурацию и секреты хранить в переменных
окружения. Использовать параметризованные запросы/SQLAlchemy expression
API. Не показывать пользователю трассировки исключений.

``` text

    schemas/task.py
    repositories/task.py
```

Router принимает запрос и вызывает сервис; Pydantic-схемы валидируют
данные; Service содержит бизнес-правила; Model описывает таблицы; DB
session создаётся на запрос и корректно закрывается. Repository
выделять, если это упрощает проект, а не ради абстракции.

## Модель данных

`Task`: PK `id`; `title` NOT NULL с ограничением длины; `description`
nullable; `status` и `priority` NOT NULL; `due_at` и `completed_at`
nullable; `created_at` и `updated_at` NOT NULL. До первой миграции
решить, добавлять ли поле владельца заранее. При переходе к нескольким
пользователям добавить `User`, FK владельца, аутентификацию и проверку
владельца при каждом запросе. Не доверять `user_id` из запроса клиента.

## API

  Метод    Путь                     Назначение
  -------- ------------------------ ------------------
  GET      `/api/tasks`             Список и фильтры
  POST     `/api/tasks`             Создать
  GET      `/api/tasks/{task_id}`   Получить
  PATCH    `/api/tasks/{task_id}`   Изменить
  DELETE   `/api/tasks/{task_id}`   Удалить

Возвращать 404 для отсутствующей задачи, 422 для ошибок валидации, 204
или 200 при удалении. Не раскрывать внутренние ошибки.

## Этапы разработки

1.  Репозиторий, окружение, зависимости и Ruff.
2.  FastAPI и тестовая страница.
3.  SQLite и SQLAlchemy 2.0.
4.  Модель Task и миграция Alembic.
5.  CRUD и сервисный слой.
6.  Схемы и обработка ошибок.
7.  Фильтры, сортировка и поиск.
8.  Веб-интерфейс.
9.  Тесты сервисов и API.
10. Docker Compose и инструкция запуска.
11. Поднять PostgreSQL, переключить подключение и проверить миграции.
12. При необходимости перенести данные отдельным скриптом, сверить
    количество записей и выполнить регрессионные тесты.

## План SQLite → PostgreSQL

Переход является отдельной учебной задачей: проверить отсутствие
зависимости от особенностей SQLite; поднять PostgreSQL через Compose;
применить Alembic-миграции; перенести данные при необходимости; сверить
данные; выполнить полный набор тестов. Не удалять SQLite до
подтверждения корректности переноса.

## Тестирование

Проверить CRUD, пустое название, ограничения длины, фильтры,
просроченные задачи, установку/очистку `completed_at`, неизвестный ID и
миграции. Использовать отдельную тестовую БД, не личную рабочую.

## Безопасность и эксплуатация

`.env` не коммитить, предоставить `.env.example`. В production
использовать HTTPS через Nginx или Caddy. При появлении авторизации
хранить только стойкие хеши паролей. Ограничить размер входных данных,
настроить резервное копирование PostgreSQL. Не запускать миграции в
каждом web worker.

## Будущее развитие

Несколько пользователей, категории, проекты, повторяющиеся задачи,
календарь, Telegram-уведомления, отдельный scheduler/worker для
напоминаний, импорт/экспорт и статистика. Telegram-привязка --- только с
доказательством владения аккаунтом.

## Критерии готовности

CRUD и фильтры работают; ошибки предсказуемы; тесты проходят; проект
запускается по инструкции; конфигурация отделена от кода; учебный этап
SQLite и план миграции на PostgreSQL документированы.
